# Changelog

## [Unreleased] — this iteration

### Added
- Full FastAPI + SQLAlchemy + MySQL backend: 16-table schema, Alembic migrations, JWT auth, section-level permission enforcement mirroring the original app's module/section matrix.
- Generic CRUD router/schema/model factory for the 8 uniform business modules (Invoices, Payments, Company Payments, Received Payments, Expenses, Freight Rates, Traders, Vehicles), driven from a single `TABLE_SPECS` registry.
- Bespoke GPS and Attendance (staff/records/holidays/monthly salary) routers, porting the original JS payroll formula exactly.
- `scripts/decompose.py`: splits the original 3MB monolithic HTML into 30 CSS files, 16 JS files, 3 de-duplicated media files, and a standalone Tax-Invoice sub-app, in original cascade/document order, byte-verified against the source. Also applies one documented, hash-verified source patch (see "Fixed" below).
- `scripts/extract_seed_data.js`: harvests the original app's hardcoded demo data (`INIT_INV`, `INIT_PAY`, `INIT_CP`, `INIT_GPS`, `INIT_FR`, `INIT_EXP`, `MONTHLY`) via a sandboxed Node VM, for faithful DB seeding.
- `app/static/js/api-client.js` (new): thin `fetch` wrapper handling JWT storage/header injection/401s for every module that talks to the new backend.
- `app/static/js/17-srt-server-auth-bridge.js` (new): bridges the legacy login UI to the real server — real JWT-based login (`srtSubmitLogin` → `srtAuthenticateAndAdoptSession`), session restore on reload (`srtRestoreSessionOnLoad`), real logout (`srtEndSession`) — without modifying any of the original 16 extracted JS files.
- `app/static/js/18-srt-registration-server-bridge.js` (new): bridges the legacy registration-request UI to the real server — public submission (`submitRegistrationRequest`), the admin's pending-requests list (`renderRegistrationRequests`) and approval modal (`openRegistrationApprovalModal`) now render live server data, and Accept/Reject (`approveRegistrationRequest` / `rejectRegistrationRequest`) call the real API, including submitting the exact module/section permissions chosen in the original permission-editor UI.
- `POST /api/auth/registration-requests/{id}/approve` now accepts an optional `modules` body so the admin's permission-editor selection at approval time is persisted server-side (previously grant-free).
- pytest suite (39 tests): auth/registration lifecycle including permission-grant-at-approval, parametrized generic CRUD (create/list/get/update/delete/404/403/409) across all 8 modules, GPS CRUD, attendance staff/day-records/holidays, and a fully deterministic salary-formula correctness test.
- Playwright browser E2E suite (6 scripts, 64 checks total, orchestrated by `scripts/run_all_e2e.py`):
  1. `e2e_login_test.py` (22 checks) — wrong/correct password, JWT storage, server-granted permissions reflected client-side, authenticated API calls from the browser, session persistence across reload, logout.
  2. `e2e_stale_credential_regression_test.py` (5 checks) — regression-proofs the stale-admin-credential fix below, including confirming the legacy safeguard still fires correctly for a *non*-server-backed session (i.e. the fix is scoped, not a blanket disable).
  3. `e2e_session_persistence_test.py` (7 checks) — tampered/invalid JWT is rejected and cleared, "Remember email" checkbox behavior.
  4. `e2e_disabled_account_test.py` (5 checks) — a `Disabled` account is rejected at login and can log in again once re-enabled, proving the rejection is status-based.
  5. `e2e_registration_test.py` (18 checks) — the complete real-UI journey: public registration submission → duplicate-email rejection → admin reviews the request on the Profile page → opens the approval modal → picks specific module/section permissions in the real permission-editor UI → approves → the new user logs in with their own chosen password → their exact granted/denied permissions are enforced by the real API from their own browser session.
  6. `e2e_permissions_test.py` (7 checks) — a view-only staff account is server-side blocked (403) from managing a granted module and from an entirely ungranted module.
- Docker Compose deployment (MySQL 8 + app, healthchecked, auto-migrate + auto-seed entrypoint).

### Fixed
- **Stale admin credential bug**: the legacy `srtLoadAccounts()` safeguard (which force-clears the session for any locally-cached admin account whose `credentialRevision` doesn't match a hardcoded constant) was silently signing the admin back out immediately after a successful, server-validated login. Root-caused and fixed at the source: `scripts/decompose.py` applies a one-line, hash-verified patch (fails loudly if the upstream line ever changes) gating the wipe condition behind `!window.SRT_SESSION_IS_SERVER_BACKED`, so any session established by `17-srt-server-auth-bridge.js` is unconditionally exempt, while the safeguard still fires correctly for a non-server-backed session. Caught only through real-browser E2E testing — invisible to API-level (pytest) tests, since it is purely a client-side JS state-management issue. Covered by a dedicated regression suite (`e2e_stale_credential_regression_test.py`).
- **`bcrypt`/`passlib` incompatibility**: `passlib[bcrypt]` 1.7.4 reads `bcrypt.__about__.__version__`, an attribute removed in `bcrypt>=4.1`, which raised on every hash/verify call. Fixed by calling the `bcrypt` library directly (`app/security.py`) instead of routing through `passlib.CryptContext`.
- **E2E test false positives** (found and fixed while getting the registration suite green): (a) a blanket "no unexpected network failures" check was flagging the exact 400/403 responses that two of the test's own negative-path assertions intentionally trigger and separately verify — fixed with a general `expected_failures: set[(status, url)]` mechanism in `scripts/e2e_helpers.py::classify_failed_response`, populated at the precise point each intentional failure is triggered; (b) `sys.exit()` inside a `finally` block was silently discarding any exception raised by a suite's `run()`, producing a misleading "0/0 checks passed" instead of a real traceback — fixed across all 6 E2E scripts by moving cleanup to an explicit `except Exception` clause that prints the traceback before recording a failed check.

### Refactored
- **Login flow** (`17-srt-server-auth-bridge.js`) split into small, single-purpose, independently-testable functions: `srtBuildAccountFromServerUser` (pure data mapping), `srtMirrorAccountLocally` (legacy-compat side effect, explicitly non-fatal), `srtAdoptServerSession` (session establishment), `srtValidateLoginForm` (pure validation, DOM-read-only), `srtAuthenticateAndAdoptSession` (the actual login round-trip), `srtRememberLoginEmail`, `srtEndSession`, `srtSubmitLogin` (thin UI orchestration only), `srtRestoreSessionOnLoad`. Each is documented with *why* it exists given the specific legacy code it bridges to, rather than being one large inline click handler.
- E2E test scripts consolidated onto shared `scripts/e2e_helpers.py`: a non-aborting `Reporter` (so one failed check doesn't hide the results of every later check in the same run), a shared `new_page()` helper with a more generous navigation timeout, and correct classification of expected vs. unexpected HTTP/console failures — distinguishing real app bugs from sandbox network restrictions (blocked CDN calls) and deliberately-triggered negative-path requests.

### Known limitations (unchanged from `docs/architecture.md` except as noted)
Notifications/Chat, the Gallery admin, and Google-Sheets sync are not yet wired to the new backend in this iteration. The Tax-Invoice sub-app remains a standalone, unmodified, client-side document (by design — it's an isolated tool, not part of the core data model). **The registration workflow is no longer a limitation**: as of this iteration, both the request-submission modal and the admin's review/approval/rejection UI are fully server-backed and covered end-to-end by browser tests.
